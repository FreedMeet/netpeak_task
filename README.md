# Netpeak Request Classifier

Класифікація вхідних запитів від внутрішніх команд (Slack/Telegram/Email) за допомогою LLM: категорія, відділ-замовник, пріоритет, короткий опис, конкретні дії та ознака "потребує уточнення".

## Як запустити

Потрібен [uv](https://docs.astral.sh/uv/).

```bash
uv sync
```

Створи `.env` у корені проєкту (шаблон — `.env.example`):

```
GEMINI_API_KEY=твій_ключ_з_Google_AI_Studio
GEMINI_MODEL=gemini-3.5-flash-lite
```

`GEMINI_MODEL` необов'язковий — за замовчуванням `gemini-3.5-flash-lite` (причина вибору саме цієї моделі — у розділі "Rate limits" нижче).

Поклади вхідний файл у `data/input_requests.csv`, потім:

```bash
uv run python -m netpeak.process
```

### Docker

```bash
docker build -t netpeak-classifier .
docker run --rm --env-file .env -v "${PWD}/output:/app/output" -v "${PWD}/google-service-account.json:/app/google-service-account.json" netpeak-classifier
```

Монтування `output/` — щоб результати залишались на хості після завершення контейнера; монтування ключа Service Account — опційне, потрібне лише якщо використовується запис у Google Sheets.

Результат:
- `output/output.json` — повний структурований результат по кожному запиту
- `output/report.md` — агрегати по категоріях/пріоритетах/відділах + список тих, що потребують уточнення

Приклади реальних прогонів (успішного і з вичерпаною квотою) — у `examples/`.

### Опційні інтеграції

**Telegram-дайджест.** Після кожного прогону надсилає короткий звіт (текстом і файлом) у чат. Додай в `.env`:

```
TELEGRAM_BOT_TOKEN=токен_від_@BotFather
TELEGRAM_CHAT_ID=id_чату_або_користувача
```

Токен отримується за пару хвилин через `@BotFather` в Telegram; `chat_id` — через `https://api.telegram.org/bot<TOKEN>/getUpdates` після першого повідомлення боту.

**Google Sheets.** Записує повний результат у таблицю (перезаписує аркуш при кожному прогоні). Додай в `.env`:

```
GOOGLE_SHEETS_SPREADSHEET_ID=id_твоєї_таблиці
GOOGLE_SERVICE_ACCOUNT_FILE=google-service-account.json
```

Потрібен Service Account у Google Cloud Console (Google Sheets API + Google Drive API увімкнені), розшарений на саму таблицю з правом Editor. JSON-ключ сервісного акаунту в репозиторій не коммітиться (є в `.gitignore`).

Обидві інтеграції — опційні: якщо відповідні змінні не задані, крок просто пропускається з INFO-логом, решта пайплайну працює як звичайно.

## Схема даних

Мінімально обов'язкові поля — `category`, `target_department`, `priority`, `short_summary`, `requested_actions`, `needs_clarification`. Додано три поля:

- **`clarification_reason`** — чому саме запит вважається розмитим (не просто `true/false`, а пояснення, яке можна показати людині, що розбирає бекграунд).
- **`possible_duplicate_of`** — якщо запит явно посилається на інший, вже наявний запит ("той самий звіт, що Оля просила"), модель фіксує це текстом. Це *не* повноцінна де-дублікація (для неї потрібен би був семантичний пошук по всій базі запитів, а не однопрохідна класифікація по одному запиту за раз) — просто сигнал, що варто перевірити вручну.
- **`target_department` — закритий список (Enum)**, а не вільний текст. Перша версія з вільним текстом давала розсинхрон у звіті (`"marketing"` / `"маркетинг"` / `"продажі"` як три різні відділи в агрегатах). Фіксований словник змусив модель нормалізувати значення прямо на етапі structured output, а не постфактум.

## Де рішення ламається / обмеження

**Невалідний вивід LLM.** Уся структура валідується через Pydantic + `response_schema` (structured output), тож модель фізично обмежена в тому, що може повернути (enum-и, типи). Якщо валідація все ж не проходить — робиться одна додаткова спроба з "repair prompt" (моделі показується її ж помилка й просять виправити). Якщо і це не допомогло — запис іде в `output.json` з `validation_error` замість `extracted`, і не валить решту пайплайну. На практиці за всі прогони repair-retry жодного разу не знадобився — `response_schema` у Gemini доволі надійний, але механізм лишається на випадок нетипових вхідних даних.

**Rate limits.** Free tier Gemini має два незалежні ліміти: RPM (запитів на хвилину) і RPD (запитів на добу), причому вони різні для різних моделей. Фактичні значення на момент розробки (Google AI Studio, dashboard "Rate Limits"):

| Модель                | RPM | TPM        | RPD |
|------------------------|-----|------------|-----|
| gemini-3.5-flash        | 5   | 1.9K/250K  | 20  |
| gemini-3.5-flash-lite   | 15  | 5.11K/250K | 500 |

Ці цифри специфічні для акаунту й моделі та можуть змінюватись з часом (Google прямо про це попереджає в документації), тож у коді вони не захардкожені — пайплайн адаптується до фактичних лімітів динамічно (див. нижче), а не покладається на ці конкретні числа.

18 запитів з `input_requests.csv` наочно показали різницю: `gemini-3.5-flash` (RPD=20) фізично не міг обробити весь файл за один прогін на free tier, `gemini-3.5-flash-lite` (RPD=500) — обробляв без проблем, тому саме він — модель за замовчуванням.

Для RPM пайплайн читає `retryDelay` із самої відповіді API і чекає рівно стільки, скільки просить сервер (адаптивний backoff), замість здогадок чи фіксованої паузи. Для RPD ретраїти безглуздо — добова квота не звільниться за секунди, тож така помилка розпізнається окремо і **не** йде в retry-цикл: пайплайн одразу зупиняється, решта необроблених запитів позначається `"skipped: daily quota exceeded"`, і коректний `output.json`/`report.md` все одно формується — замість зависання на годинах марних повторів (приклад такого прогону — в `examples/`).

**Недетермінізм.** `temperature=0.0` виставлено для максимальної відтворюваності, але це не гарантія ідентичного виводу між різними прогонами чи моделями. На реальних даних це видно неодноразово: той самий запит (REQ-003, про інтеграцію транскриптів дзвінків з PlanFix) `gemini-3.5-flash` класифікував як "автоматизація", а `gemini-3.5-flash-lite` — як "інтеграція"; REQ-016 (питання про якість відповідей асистента) між прогонами хитався між "питання/консультація" і "баг/підтримка". Обидва варіанти в кожній парі по-своєму логічні — це не помилка, а межові випадки класифікації, варті згадки, а не приховування.

**Вартість токенів.** Обробка 18 коротких запитів на free tier безкоштовна. Для більших обсягів вартість масштабується лінійно з кількістю запитів, кожен з яких — окремий виклик API (по одному запиту на рядок, без батчингу в один prompt). При тисячах запитів варто або пакетувати кілька запитів в один виклик (з ризиком плутанини полів між ними), або переходити на платний тір з вищими лімітами. На практиці, навіть з урахуванням кількох повторних прогонів під час розробки і ретраїв через rate limit, сумарний TPM-показник за добу лишався в межах кількох відсотків від ліміту free tier (250K TPM) — тобто для такого обсягу вузьким місцем є саме RPM/RPD, а не вартість/об'єм токенів.

**Великий обсяг.** Поточна реалізація синхронна, по одному запиту за раз — свідомий вибір: боттлнеком є не швидкість власного коду, а RPM-ліміт самого API, тож паралелізм (async/threads) на free tier нічого б не пришвидшив, лише швидше вичерпав би квоту. Якщо колись з'явиться платний тір без RPM-обмежень — це перше місце, де варто додати паралельну обробку.

**Провайдер.** Реалізація захардкожена під Gemini (`google-genai`) — завдання прямо дозволяє обрати одного провайдера, тож абстракція під кількох (OpenAI/Anthropic/Gemini) свідомо не робилась, аби не роздувати обсяг без потреби.

## Що зробили б далі, якби було більше часу

- Абстракція над LLM-провайдером (Protocol/ABC + реалізації), якщо знадобиться підтримка кількох.
- Справжня де-дублікація запитів через embedding-пошук по вже оброблених запитах, а не покладання на те, що модель сама розпізнає посилання в тексті.
- Батчинг кількох коротких запитів в один виклик LLM для економії токенів на великих обсягах.
- Юніт-тести на Pydantic-валідацію (навмисно зіпсовані JSON-відповіді) та на агрегацію в `report.md`.
